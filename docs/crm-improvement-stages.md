# CRM改善の残作業と段階

更新: 2026-11-12

## 第1段階：対象外・要確認と返信下書き

実装済み。

- 活動一覧を「送信候補」「要確認（作業が必要）」「今回の一括送信対象外」で絞り込む。学校で絞り込んでも、条件に合うコーチだけを表示する。
- 返信済み・対応終了・個別対応中の対象外は、宛先不備などの修正作業と区別する。対象外に宛先不備があっても、一括送信のための修正作業には加算しない。
- 今回の送信結果不明・返信の対応付け未確定は要確認として保留。過去の活動にしか紐付かない計測・予約を混ぜない。共有宛先の送信結果不明は両コーチに反映する。
- Staff要確認などの保留判定はrecruiting-status.jsへ集約し、候補校と活動一覧で共通化する。
- 活動のメール詳細から個別CRMへ進み、履歴・送信結果を照合できる。
- 個別CRMの返信原稿に「下書きを保存」「保存済みを復元」を追加。件名・本文・方針・CC・日本語訳・分析・作成理由等を保存する。保存は明示操作で、自動送信・自動予約ではない。
- 元のコーチ・Gmailスレッド・元返信時刻・返信本文で下書きを識別する。別のコーチや新しい返信へ古い原稿を自動復元しない。
- 再読み込み後、現在の入力が空の場合に保存済みを復元する。読み込み中の入力・AI処理・遅延応答を上書きしない。
- 保存時のrevisionを照合し、別画面で更新された原稿を無言で上書きしない。競合時は現在の入力を残して再確認を促す。
- 復元時は進捗の提案を再確認待ちにし、進捗・宛先・CCの送信前確認を引き継がない。既存のGmailの送信済み判定・元メール照合を維持する。
- recruiting_reply_draftsとsave_recruiting_reply_draft RPCは所有者のみ。RLS・他ユーザーからの読み取り/更新/RPC拒否・匿名RPC不可・競合拒否をDBで検証。試験用の保存はすべてロールバック。

検証: tests/reply-draft-storage.cjs、tests/activity-disposition.cjs、既存の返信・送信UI・コーチ導線・ナビゲーション・活動集計テスト。実メール・AI処理・予約・一括ラベル操作は行っていない。

## 第2段階：送信・予約・Gmail連携

未着手。実際の日時・文面を確定する前に仕組みと模擬試験を完成させる。

1. 旧カリフォルニア専用の初回送信処理と生涯Follow-up回数への依存を解消し、今回の活動ID・初回/FU1/FU2・元スレッドを使って準備から実績記録までつなぐ。
2. 予約前と送信直前に、学校単位の返信・問い合わせ・対象外・要確認を同じ条件で確認する。返信が来た学校の今回の一括アプローチ予約を停止する。返信学校の個別返信・会話後のFollow-upとは分ける。
3. 共有宛先は1通に集約し、両コーチへ実績を反映。既存予約との重複も検査する。
4. 活動を識別するラベルと既存の対応状態ラベルを両立させる。過去のラベルを一括変更しない。
5. 送信結果不明・返信の対応付け・Gmailラベル同期失敗を保存し、照合・再同期できるようにする。第1段階の要確認へ結び付ける。

未着手。PC・スマホで候補校、個別CRM、文案の保存/復元、予約前確認、返信反映まで一連の操作を確認する。実際の予約・コーチへの送信は、ユーザーの②学校別日程と③メール内容の確定後に行う。
