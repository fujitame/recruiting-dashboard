# CRM改善の残作業と段階

更新: 2026-11-12

## 第1段階：対象外・要確認と返信下書き

実装済み。

- 活動一覧を「送信候補」「要確認（作業が必要）」「今回の一括送信対象外」で絞り込む。学校で絞り込んでも、条件に合うコーチだけを表示する。
- 返信済み・対応終了・個別対応中の対象外は、宛先不備などの修正作業と区別する。対象外に宛先不備があっても、一括送信のための修正作業には加算しない。
- 今回の送信結果不明・返信の対応付け未確定は要確認として保留。過去の活動にしか紐付かない計測・予約を混ぜない。共有宛先の送信結果不明は両コーチに反映する。
- Staff要確認などの保留判定はrecruiting-status.jsへ集約し、候補校と活動一覧で共通化する。
- 活動のメール詳細から個別CRMへ進み、履歴・送信結果を照合できる。
- 個別CRMの返信原稿に「下書きを保存」「保存済みを復元」を追加。件名・本文・方針・CC・日本語訳・分析・作成理由等を保存する。保存は明示操作で、自動送信・自動予約ではない。
- 元のコーチ・Gmailスレッド・元返信時刻・返信本文で下書きを識別する。別のコーチや新しい返信へ古い原稿を自動復元しない。
- 再読み込み後、現在の入力が空の場合に保存済みを復元する。読み込み中の入力・AI処理・遅延応答を上書きしない。
- 保存時のrevisionを照合し、別画面で更新された原稿を無言で上書きしない。競合時は現在の入力を残して再確認を促す。
- 復元時は進捗の提案を再確認待ちにし、進捗・宛先・CCの送信前確認を引き継がない。既存のGmailの送信済み判定・元メール照合を維持する。
- recruiting_reply_draftsとsave_recruiting_reply_draft RPCは所有者のみ。RLS・他ユーザーからの読み取り/更新/RPC拒否・匿名RPC不可・競合拒否をDBで検証。試験用の保存はすべてロールバック。

検証: tests/reply-draft-storage.cjs、tests/activity-disposition.cjs、既存の返信・送信UI・コーチ導線・ナビゲーション・活動集計テスト。実メール・AI処理・予約・一括ラベル操作は行っていない。

## 第2段階：送信・予約・Gmail連携

実装・反映済み。実行は無効。日時・文面の承認フラグは未設定。今回の送信予約・実送信は0件。

- 「予約前チェック」でコーチ数と実際の宛先数、除外・要確認・文案未入力の理由、日本時間と学校現地時刻、保存済み件名・本文を確認する。
- 活動ID・宛先・学校・初回/FU1/FU2ごとのキューを追加。直前の同一活動の送信済みスレッドをFUの元にする。生涯Follow-up回数を初期化せず、新活動の回数判定にも使わない。
- 共有宛先は学校内で1通に集約。件名・本文・日時案が違えば予約を保留する。「共有宛先の全コーチに保存」で明示的にそろえる。保存元のスナップショットを照合し、他画面の変更を上書きしない。
- 送信候補・予約・送信直前に同じDB判定を使う。学校内の別コーチ、過去の返信、問い合わせ、活動の返信・進捗、スタッフ確認、宛先不備、別校との宛先重複、旧予約、送信結果不明を確認する。送信直前にはGmailの既知スレッドと学校の既知送信者も調べる。
- 返信・問い合わせ・個別対応の記録で学校の新活動の予約を停止。処理中は取消フラグと送信直前のゲートで停止する。GmailとDBは別システムなので、その間の返信到着を完全に原子的に排他することはできない。受理済み送信は実績として保存する。
- 実送信の固定Message-ID、送信本文、宛先、件名、送信済みラベル、FUの元スレッドで検証。ネットワーク障害・読戻し不一致・記録失敗・中断では自動再送しない。「Gmailと送信結果を照合」は読み取りと記録の確定だけを行う。
- 検証済み送信は共有宛先の両コーチへ1回ずつ反映。同じ実送信の再確定で回数を増やさない。履歴のGmail ID一意制約を維持し、他の共有コーチは履歴本文と活動の共通tracking_idで同じ送信に結び付ける。
- 活動ラベルは新活動の実メールだけへ付与。従来の対応状態ラベルと併用し、他のラベルを保持。実際の最新返信・送信でNeeds Reply / Waitingを判定し、旧FU回数によるNo Responseへの誤分類を防ぐ。
- ラベル同期の失敗を永続保存し、再試行用のキューと「ラベルだけ再同期」を追加。送信・返信の対応付け・ラベルの問題は「連携の要確認」から確認できる。ラベルのみの失敗はメール再送につなげない。
- 返信検出へ今回の送信スレッドを登録。未知の返信者は学校を確認待ちにし、先頭コーチへ誤って割り当てない。重複取り込みでも未解決のラベル同期を再試行する。
- コーチ連絡先・個別CRMの未返信への送信導線を今回の活動へ集約。今回の次の段階・予約・保留の詳細を開く。旧予約画面は履歴確認にし、旧初回・FU・一括予約の本番経路は画面・Edge・DBで新経路へ案内する。個別返信と返信後Follow-upは従来の確認付きフローを保持。テスト予約は固定宛先の既存処理を保持。
- 所有者のみの読み取り、認証ユーザーによる実行フラグ変更・キュー直接作成の拒否、サービス専用RPC、匿名拒否を確認。返信停止トリガーの権限は停止処理だけに限定し、固定search_pathを設定する。

検証: tests/campaign-outreach.sql（全操作ROLLBACK）、campaign-worker.cjs、campaign-reconciliation.cjs、campaign-labels.cjs、campaign-preparation.cjs、legacy-campaign-routing.cjs、既存の返信原稿・送信UI・導線・状態・集計テスト。新APIの未認証リクエストは403。新規テーブル・関数のセキュリティ検査に新しい指摘なし。

本番運用の有効化は②学校別日程と③メール内容の確定、ログイン後の操作確認を終えてから。新workerの定期実行はまだ登録していない。既存の返信取得は10分ごとの処理を維持する。過去のラベルの一括変更は行っていない。

## 第3段階：ログイン後の通し確認

実画面で認証画面まで確認済み。認証済みブラウザがないため、以下の最終確認はログイン後に行う。

- PC・スマホで候補校 → 学校評価シートのオーバーレイ → 個別CRM → 今回の準備 → 予約前チェックを確認。
- 下書き保存・復元・共有宛先への保存、活動/段階の切り替え、要確認からの導線、表示幅とスクロールを確認。
- ②③未確定のため予約ボタンが無効であることを確認。承認後のテストは固定宛先の許可されたテストだけで行う。

実際のコーチへの送信・予約は行わない。
