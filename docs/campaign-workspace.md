# 活動状況・送信準備

2026年11月の再アプローチを、従来の活動と分けて管理する画面。

## 画面と導線

- CRM上部「活動状況・送信準備」から同じウィンドウ内で開く。
- 活動、学校／コーチ、今回初回／Follow-up 1／Follow-up 2を切り替える。
- 4種類の円グラフの凡例を押すと対象一覧を絞り込む。返信・進捗は常に学校単位。
- 送信準備からコーチごとの件名・本文・送信日時案を保存できる。日時は日本時間入力、UTC保存。
- 日時案の保存は実際の送信予約ではない。実際の送信日時は②、文面の確定は③で扱う。
- 学校名は既存の評価シートをオーバーレイ表示。学校の返信・進捗、コーチの全履歴もオーバーレイで確認。
- 従来の連絡履歴・返信対応・個別CRMと予約管理は引き続き利用可能。

## 集計と対象

- 対象作成時に、いずれかのコーチの返信履歴・返信本文・返信ステータス・紐付き問い合わせがある学校を学校全体で除外。
- 対象作成後の返信は対象コホートの実績として残し、その学校の全コーチを一括送信の除外表示にする。
- 未紐付けの有効な問い合わせは、メールアドレスが既存コーチと一致した場合も学校全体を除外表示。dismissedは返信とは扱わない。
- 宛先ありは在職・アドレスの最終確認完了を意味しない。無効形式のアドレス、過去にClose・候補外とした連絡先は要確認。
- 同校・同宛先への実送信は1通に集約する前提。コーチ集計では対象者全員に同一メールの実績を反映する。
- 初回ジョブのcampaign_key、明示的に紐付けたFollow-up予約、campaign_messages.tracking_idのみ今回の実績とする。日時・過去の累計カウンターだけで振り分けない。
- 共有宛先の初回ジョブはcontact_ids全員に紐付け。Follow-upはreservation_item_idを明示したものだけを今回に集計。
- 学校内で送信状態が異なる場合は混在区分に集計する。
- 反応の円グラフはYouTube、Profile、開封の兆候、反応未検知、計測メールなしの優先順。重複した実数も併記する。自動スキャンの専用記録は加算しない。
- 反応未検知は未読の証明ではない。計測対象がないものと分ける。
- Gmail返信同期ではIn-Reply-Toの直接の親メールを、Gmailスレッド内のRFC Message-IDで特定し、今回の送信記録と照合する。過去の親メールへの返信は今回へ加算しない。
- 返信先を特定できない場合は「対応付け要確認」。過去のスレッドも保存済みジョブから追跡し、現在のコーチレコードのスレッドだけに限定しない。
- 関心・キャンプ・面談・条件提示・オファーなどは学校単位で明示保存。返信だけで関心ありにしない。
- 手動で返信ありとする場合は、今回の返信の件名やメッセージID等を必須にする。

## 保存と権限

4つの活動テーブルはRLSで所有者に限定。計測・予約を紐付ける場合も所有者、対象コーチまたは同校の共有宛先、送信段階を照合する。従来の連絡先・履歴はリセットしない。

- `node tests/campaign-workspace.test.cjs`: 過去活動・段階の分離、学校内混在、学校全体の除外、明示したFollow-up予約、問い合わせ、宛先形式。
- `node tests/campaign-reply.test.cjs`: 返信の親メール、旧活動の返信、特定不能、確定状態の維持、送信前の返信、Edge Function構文。

- 公開ページとログイン案内をブラウザで確認。ログイン後の実画面操作は未確認。
- 送信・送信予約はこの実装作業では作成していない。

## ②③との接続

日時・文案確定後に、今回のcampaign_keyを初回送信ジョブへ渡す。Follow-upは今回の活動内の回数と送信元スレッドを使って予約し、各campaign_messagesへreservation_item_idを記録する必要がある。従来の予約画面の生涯カウントだけで今回のFollow-upを判断しない。この送信側の接続と実予約は②③確定後の作業。

## Gmailラベル

- 「Gmail返信を取り込む」で既存の返信取り込みを実行し、その結果とGmailラベルの失敗件数を画面へ表示する。「表示を更新」はDB表示の再取得のみ。
- `Recruiting/Waiting Coach`、`Recruiting/Needs Reply`、`Recruiting/Follow-up Due`、`Recruiting/No Response`、`Recruiting/Closed`が既存の対応状態ラベル。状態変更ではこの5種類だけを付け替え、他の分類ラベルを削除しない。
- 返信取り込み時はスレッドの実際の最終送受信時刻を確認し、未返答の返信がある場合にNeeds Reply、こちらが後から返答済みならWaiting Coachにする。遅れて取り込んだ古い返信だけでNeeds Replyへ戻さない。
- ラベルの失敗で保存済みの返信・履歴を取り消さない。失敗は件数とエラーに残す。
- 活動の識別と対応状態ラベルを別の軸として扱う。新活動の送信側を②③の後で接続する際に、旧活動のラベルの一括付け替えを行わず、新しく送受信したメールにだけ活動区分を付ける。旧累計のFollow-up回数で新活動のNo Responseラベルを決めない。
- この実装作業で既存メールに対する一括ラベル変更は実行していない。
